# Git 컨벤션

## 브랜치 네이밍 규칙

### 형식

```
<type>/<description>
```

### 타입

| Type       | 설명        | 예시                    |
| ---------- | ----------- | ----------------------- |
| `feat`     | 새로운 기능 | `feat/portfolio-crud`   |
| `fix`      | 버그 수정   | `fix/auth-token-expire` |
| `refactor` | 리팩토링    | `refactor/user-service` |
| `hotfix`   | 긴급 수정   | `hotfix/login-error`    |
| `chore`    | 빌드, 설정  | `chore/docker-setup`    |
| `docs`     | 문서 작업   | `docs/api-spec`         |

### 규칙

- 소문자 사용
- 단어 구분은 하이픈(`-`)
- Issue 번호는 선택 사항 (이슈가 있는 작업이면 브랜치명 끝에 `-#<issue_number>` 첨부 가능)

## 브랜치/환경 매핑

### 기본 규칙

- `dev` 브랜치: 개발 서버 배포 (APP_PROFILE=dev)
- `main` 브랜치: 프로덕션 서버 배포 (APP_PROFILE=prod)

### 배포 구성

- 개발 서버: `docker-compose.infra.yml` + `docker-compose.dev.yml` + `.env.dev` (Blue-Green)
- 프로덕션 서버: `docker-compose.infra.yml` + `docker-compose.prod.yml` + `.env.prod` (Blue-Green)

### 릴리스 흐름

1. 기능 브랜치 → `dev` PR
2. 검증 완료 후 `main` PR

## 커밋 메시지 컨벤션

### 형식

```
<type>: <subject> (#<issue_number>)

<body>
```

관련 이슈가 없는 경우 `(#<issue_number>)` 부분은 생략합니다.

### 타입

| Type       | 설명                                        |
| ---------- | ------------------------------------------- |
| `feat`     | 새로운 기능 추가                            |
| `fix`      | 버그 수정                                   |
| `docs`     | 문서 수정                                   |
| `style`    | 코드 포맷팅, 세미콜론 누락 등 (기능 변경 X) |
| `refactor` | 코드 리팩토링                               |
| `test`     | 테스트 코드 추가/수정                       |
| `chore`    | 빌드 설정, 패키지 매니저 등                 |
| `rename`   | 파일/폴더 이름 변경 또는 이동               |
| `remove`   | 파일 삭제                                   |

### 커밋 메시지 규칙

1. **제목은 50자 이내**
2. **제목 끝에 마침표 없음**
3. **제목은 명령문으로 작성** (한글: ~구현, ~수정, ~추가)
4. **본문은 72자마다 줄바꿈**
5. **본문에 What, Why 설명**
6. **이슈 번호는 선택 사항** — 관련 이슈가 있는 경우에만 `(#<issue_number>)`를 포함

### 예시

```bash
# 좋은 예시
git commit -m "feat: 포트폴리오 생성 API 구현 (#15)

- POST /portfolios 엔드포인트 추가
- CreatePortfolioDTO 정의
- Swagger 문서 업데이트"

# 간단한 커밋
git commit -m "fix: 토큰 만료 시간 오류 수정 (#23)"

# 문서 수정
git commit -m "docs: API 명세서 업데이트 (#12)"

# 관련 이슈가 없는 경우
git commit -m "chore: pnpm 버전 업데이트"
```

### 금지 사항

AI가 생성했다는 표시 **절대 금지**:

```bash
# 절대 사용 금지
Co-Authored-By: Claude <noreply@anthropic.com>
Generated with Claude Code
Generated by AI
```

## 이슈 (백로그)

이슈 생성은 선택 사항입니다. 간단한 작업은 이슈 없이 바로 브랜치/커밋을 생성해도 되며,
추적이 필요한 작업만 `.github/ISSUE_TEMPLATE/backlog.md` 템플릿으로 가볍게 기록합니다.

- 제목: 무엇을 할지 한 줄로 알 수 있게 자유롭게 작성 (`[TYPE]` 접두사 불필요)
- 본문: 설명 + 참고 사항(선택) 정도면 충분 — 상세 스펙 문서화가 필요하면 별도 문서로 링크

## PR 제목 컨벤션

### 형식

```
TYPE: 설명 (#이슈번호, 선택)
```

관련 이슈가 없는 경우 `(#이슈번호)` 부분은 생략합니다.

### 예시

```
Feat: 포트폴리오 CRUD API 구현 (#15)
Fix: 로그인 토큰 갱신 오류 수정
Refactor: 사용자 서비스 리팩토링
Chore: Docker 설정 추가
Docs: API 문서 업데이트
```

## PR 템플릿

`.github/PULL_REQUEST_TEMPLATE.md`는 변경 사항을 문서화하는 용도입니다.
체크리스트성 게이트가 아니라 리뷰어가 변경 내용을 빠르게 파악하기 위한 최소 정보만 담습니다.

- **요약**: 무엇을, 왜 변경했는지
- **변경 사항**: 주요 변경 bullet
- **배포 대상**: `Dev` / `Prod`
- **관련 이슈**: 있으면 연결, 없으면 생략
- **참고 사항**: 테스트 방법, 스크린샷 등 필요한 경우에만

## 코드 리뷰 시 참고 사항 (권장)

- 브랜치명/커밋 메시지가 컨벤션을 따르는가?
- 로컬에서 빌드/테스트가 통과하는가?
- Docker 빌드가 성공하는가? (Dockerfile 변경 시)
- 불필요한 console.log가 없는가?
- 코드 포맷팅이 적용되었는가?

## Docker 빌드 가이드

### pnpm 버전 관리

Dockerfile의 pnpm 버전은 로컬 개발 환경과 일치시켜야 합니다:

```dockerfile
# package.json의 packageManager 필드 확인 후 동일한 버전 사용
RUN corepack enable && corepack prepare pnpm@10.28.0 --activate
```

### npm scripts의 CI 환경 대응

Git hooks 관리 도구(husky 등)는 `.git` 폴더가 없는 CI/Docker 환경에서 실패할 수 있습니다.
`prepare` 스크립트는 `.git` 폴더 존재 여부를 확인해야 합니다:

```json
{
    "scripts": {
        "prepare": "node -e \"if (require('fs').existsSync('.git')) { require('child_process').execSync('husky', {stdio: 'inherit'}) }\""
    }
}
```

**주의사항:**

- `.dockerignore`에 `.git`이 포함되어 있어 Docker 컨테이너에는 Git 정보가 없음
- `pnpm install` 실행 시 `prepare` 스크립트가 자동으로 실행되므로 조건부 처리 필수
- `.git`이 있는 환경에서는 husky 실행 오류가 정상적으로 전파되어 설정 문제를 즉시 발견 가능

### 로컬 Docker 빌드 테스트

PR 생성 전 로컬에서 Docker 빌드를 테스트하세요:

```bash
# 빌드 테스트
docker build -t folioo-server .

# 전체 단계 테스트 (DB 포함)
docker compose up -d
```
